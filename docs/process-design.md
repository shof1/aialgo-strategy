対象: 系統用蓄電所（BESS）向け、JEPX スポット / EPRX / JEPX 時間前 / OCCTO 計画提出の自動運用ボット
構成: Next.js on **Vercel** / **Supabase** (Postgres + pg_cron + Edge Functions) / **GitHub**（コード・変更履歴）

## 1. 基本概念

### 1.1 日付コード（Delivery Day = D）
- `date_code = YYYYMMDD`（例 `20261112`）＝ **受渡日 D**
- 1つの日付コードに紐づくタスク群を **Run** と呼ぶ（`runs` テーブル 1 行 = 1 日付コード）
- Run の寿命: **D-1 09:00 → D 24:00（+ 翌朝の精算・振り返り）** ＝ 約 39 時間

### 1.2 二重並行（オーバーラップ）
毎日、2 つの Run が同時に動く。

| 時刻（暦日 T） | Run D=T+1（準備フェーズ） | Run D=T（受渡フェーズ） |
|---|---|---|
| 00:00–09:00 | — | 時間前取引ループ |
| 09:00–17:00 | スポット取得・EPRX 入札・OCCTO 提出 | 時間前取引ループ（並行） |
| 17:00–22:40 | SOC 計画・時間前の初期入札 | 時間前取引ループ（終盤） |
| 22:40– | B01 への入札開始 → 受渡フェーズへ移行 | 終了 → 精算 |

→ **スケジューラは「時刻」ではなく「(date_code, step)」単位でジョブを発行**し、同時刻に 2 Run 分のジョブが走っても衝突しない設計にする。共有資源（**バッテリー SOC と kW 枠**）だけはロックで排他する。

## 2. Run の状態遷移（ステートマシン）

```
CREATED
  │ D-1 09:00
  ▼
PREP_STARTED ──(10:30)──▶ SPOT_FETCHED
  │                          │ 13:00
  │                          ▼
  │                       EPRX_BID_PLANNED ──(≤14:00 提出)──▶ EPRX_BID_SUBMITTED
  │                                                              │ 15:00
  │                                                              ▼
  │                                                          EPRX_AWARDED
  │                                                              │ 16:00
  │                                                              ▼
  │                                                          OCCTO_PLAN_READY ──(≤17:00)──▶ OCCTO_SUBMITTED
  │                                                                                              │
  │                                                                                              ▼
  │                                                                                          SOC_PLANNED (B01–B48)
  │                                                                                              │
  │                                                                                              ▼
  │                                                                                          HA_INITIAL_BIDS_PLACED
  │                                                                                              │ D-1 22:40
  │                                                                                              ▼
  │                                                                                          INTRADAY_LOOP (毎 :10 / :40)
  │                                                                                              │ 最終コマ GC 後
  │                                                                                              ▼
  │                                                                                          DELIVERED → SETTLED → CLOSED
  │
  └── いずれのステップでも ──▶ FAILED / MANUAL_HOLD（人手介入待ち、Trade Results に警告）
```

各ステップは **冪等**（同じステップを再実行しても二重入札しない）にする。`run_steps` に `(date_code, step)` のユニーク制約を張り、完了済みならスキップ。

## 4. 意思決定ロジック（初版は ルール + AI 推定）

### 4.1 EPRX 入札（S2）
1. 特徴量: 当日スポット価格（コマ別）、過去 N 日の EPRX 約定価格（同曜日・同時間帯）、予備率、季節
2. モデル: 初版は **ルールベース + 単純回帰**（スポット高値帯・予備率低下帯にスコア付け）→ 上位 7 コマ
3. 価格: 過去約定分布のパーセンタイル（例 P60）を基準、予備率が低いほど強気
4. 制約: 選んだコマで SOC が調整余力を出せること（2 MW × 0.5 h = 1 MWh / コマ分の kWh を確保）
5. 7 コマの根拠: 8 MWh ÷ 1 MWh = 8 コマ、充放電ロス分を引いて 7 コマ

### 4.2 時間前 ラダー入札（S8）
| 方向 | 条件 | 量 |
|---|---|---|
| 買（充電） | 価格 `< 1 円/kWh` | 最大 7 コマ（各 1 MWh）。ただし **SOC 上限までの空き**で制限 |
| 売（放電）段 1 | 価格 `> 30 円` | 段 1・段 2 合計で最大 7 コマ |
| 売（放電）段 2 | 価格 `> 40 円` | 同上（段 1 より高値を優先して割当） |
| 段 n … | `strategy_params` で追加 | — |

- しきい値・量配分は `strategy_params` テーブルで管理（画面から変更可、変更履歴を残す）
- EPRX 約定コマは時間前入札対象から除外（その時間帯は調整力として kW を確保済み）
- **SOC 制約チェック**: 全注文が約定した場合でも、各コマ時点の SOC が `[min_soc, max_soc]` に収まること（往復効率 η はパラメータ、初期値 0.85 を仮置き）

### 4.2a スポット連動しきい値（v0.4、既定）
固定しきい値（買 `< 1 円` / 売 `> 30・40 円`）は、2026/10/15〜11/13 の東京スポット（中央値 30.1 円、1 円未満は 1,440 コマ中 8 コマ）では
ほとんど約定しない。そこで D-1 10:30 に確定しているスポット約定価格を、そのコマの時間前の基準価格として使う。

| 項目 | ルール |
|---|---|
| 指値 | 買 = そのコマのスポット + `buyOffsetYen`、売 = スポット + `sellOffsetYen` |
| コマ選定 | （充電 c, 放電 d, c < d）の組を `売指値[d] × η − 買指値[c]` の大きい順に採用。`minSpreadYen` 未満は捨てる |
| SOC | 組を足すたびに時刻順の SOC を検算し、どちらかが 1 コマの半分未満しか出せなくなる組は採用しない |
| 持ち越し | 開始 SOC に余りがあれば、組にならない高値コマでも売る（その日の最安コマを買うより得な場合だけ） |
| パラメータ選定 | `npm run sweep`: 直前 60 日で純損益（保守的判定）最大のオフセットを選び、次の 30 日で評価。検証期間は選定に使わない |

`thresholdMode = "fixed"` にすると v0.2 の方式に戻る（`FIXED_PARAMS`）。

### 4.3 イントラデイループ（S9、30 分毎）
時間前のゲートクローズ（GC）は受渡開始の 1 時間前。各サイクルで **直後に GC を迎えるコマ** が最終判断対象になる。

| 実行時刻 | 最終判断対象 | GC |
|---|---|---|
| D-1 22:40 | B01（00:00–00:30） | 23:00 |
| D-1 23:10 | B02（00:30–01:00） | 23:30 |
| D HH:40 | HH+2:00 開始のコマ（実行 + 80 分） | HH+1:00 |
| D HH:10 | HH+1:30 開始のコマ（実行 + 80 分） | HH:30 |
| D 22:10 | B48（23:30–24:00） | 22:30 |

```
1. 実 SOC 取得（BMS/EMS）→ soc_readings
2. 計画 SOC との乖離を計算
3. 最終判断対象コマ: 確定させる（未約定注文の取消/価格修正、乖離補正の追加注文）
4. それ以降のまだ GC 前のコマ: 価格・量を見直し
5. 約定を取り込み、soc_plan を再計算（将来コマ）
6. action_logs に記録
```

---

### 4.3a 売り切り優先（v0.5、`catchupYen`）
売り指値がスポット連動のままだと、時間前の平均がわずかに届かず売りが残り、SOC が翌日へ持ち越される（例 ID:20261116）。
S9 の各売りコマで次を判定する:

- このコマ以降の残り売りコマ数を R、受渡端で売れる電気 = (SOC − 下限) × √η とする
- それが「このコマを除く R−1 コマ × 1 MWh」を超える（＝このコマを逃すと売り切れない）とき、売り指値を `catchupYen` 円下げる
- ただし原価割れはしない: 下限 `floorYen` = 計画した買い指値の平均 ÷ η

`catchupYen` は sweep で他のオフセットと同時に選ぶ。選定指標は**在庫補正後の損益**
（純損益 + (終了 SOC − 開始 SOC) × √η × 期間平均スポット）。期首在庫の売却益で選ばないため。

## 5. システム構成

```
┌──────────── Vercel (Next.js) ─────────────┐
│ 画面: Dashboard / Trade Results / Params   │
│ API: /api/jobs/[step]  (ジョブ実行口)      │
└───────────────▲───────────────────────────┘
                │ HTTPS (署名付き)
┌───────────────┴──── Supabase ─────────────┐
│ pg_cron ─▶ job_queue へ投入 ─▶ 実行呼出   │
│ Postgres: runs, run_steps, action_logs ... │
│ Auth（画面ログイン）/ RLS                  │
└───────────────────────────────────────────┘
        │                         │
   外部: JEPX / EPRX / OCCTO   設備: BMS/EMS（SOC）
GitHub: コード + migrations + strategy 変更履歴（PR）
```

### 5.1 外部接続（API + ブラウザ画面操作の自動化）
| 接続先 | 方式 | 備考 |
|---|---|---|
| JEPX（スポット結果・時間前） | API があれば API、無ければ画面操作 | 要確認: 利用可能な API 仕様 |
| EPRX（入札・約定） | 同上 | |
| OCCTO（予備率取得・計画提出） | 同上 | |
| BMS / EMS（SOC） | API | **未確認**: 取得元システム |

- 画面操作の自動化は **Playwright**（ヘッドレス Chromium）で実装
- Vercel のサーバーレス関数は実行時間とブラウザ実行に制約があるため、画面操作は **専用ワーカー**（常駐の小型 VM / コンテナ。例: Fly.io、Railway、自社サーバー）で実行し、Supabase の `job_queue` を取りに行く方式にする
- 各接続は `Connector` インターフェース（`fetch` / `submit` / `status`）で抽象化し、API ⇔ 画面操作 ⇔ バックテスト用モックを差し替え可能にする
- 画面操作は失敗しやすいので、操作ごとにスクリーンショットを Supabase Storage に保存し `action_logs` から参照

### 5.2 スケジューラ（推奨: Supabase pg_cron）
- Vercel Cron は Hobby プランだと 1 日 1 回まで、関数実行時間にも上限があるため、**30 分毎ループと締切監視は pg_cron 側**に置く
- pg_cron → `job_queue` に `(date_code, step)` を投入 → Vercel API / Supabase Edge Function を呼ぶ
- 実行はリトライ付き（指数バックオフ）、締切の 10–15 分前に未完了ならアラート

**毎日の cron 定義（JST）**
| cron | ジョブ |
|---|---|
| `0 9 * * *` | S0 Run(D=明日) 起票 |
| `30 10 * * *` | S1 |
| `0 13 * * *` | S2 → S3 |
| `0 15 * * *` | S4 |
| `0 16 * * *` | S5 → S6 |
| `0 17 * * *` | S7 → S8 |
| `10,40 * * * *` | S9（対象 Run を status から自動判定。日中は Run D、22:40 以降は Run D+1 も） |
| `0 8 * * *` | S10 Run(D=昨日) 精算 |

## 8. 運用モードと安全装置

- **mode = `test`（初期）**: 外部への提出は行わず、データ取得と意思決定・仮想約定のみ記録（ペーパートレード）
- **mode = `live`**: 提出あり。切替は画面から、ログに記録
- キルスイッチ（全注文停止）、1 コマ・1 日あたりの最大取引量上限、SOC ハードリミット
- 秘密情報（各市場の認証情報）は Supabase Vault / Vercel 環境変数。コードに置かない

### 8.1 バックテスト（過去 1 ヶ月）
- **期間**: 直近 1 ヶ月（例 2026-10-14 〜 2026-11-13、30 Run）
- **データ**: JEPX スポット（東京エリア 48 コマ）・JEPX 時間前約定・EPRX 約定結果・広域予備率を `historical_*` テーブルに取込み（JEPX スポットは公開 CSV で取得可）
- **方法**: 本番と同じ意思決定コード（S2, S7, S8, S9）を `Connector` のバックテスト版に差し替えて日付コードごとに再生
  - 約定判定: 自分の入札価格と実際の約定価格を比較（買: 実価格 ≤ 入札価格、売: 実価格 ≥ 入札価格）
  - 時間前は 30 分毎のループを、そのコマの約定価格（またはその時点の VWAP）で近似
  - 市場への価格影響は無いものとする（2 MW は小さいため）
- **出力**: Run 毎の PnL（スポット/時間前の売買差益 + EPRX 収入 − 充放電ロス）、約定率、SOC 推移、制約違反の有無
- **画面**: Trade Results に `mode=backtest` の Run として表示（本番 Run と同じ画面で比較）
- **ベースライン比較**: 「スポットの安値 7 コマ充電・高値 7 コマ放電」単純戦略と比べる

## 9. 決定事項と残りの確認事項

**決定（v0.2）**
- B01 への入札は **D-1 22:40** から開始（GC 23:00）
- EPRX は **30 分 × 7 コマ**（2 MW / 8 MWh、ロス考慮）
- 買 `< 1 円` は最大 7 コマ（SOC で制限）、売 `> 30 円` / `> 40 円` は合計最大 7 コマ
- 接続は API + ブラウザ画面操作の自動化
- バックテストは過去 1 ヶ月
- 東京エリア、2 MW / 8 MWh

**残りの確認事項**
1. **SOC の取得元**: BMS / EMS のどのシステムから、どの方式（API 名・ポーリング間隔）で取るか
2. **API と画面操作の割り振り**: JEPX / EPRX / OCCTO のうち API を使えるのはどれか（各社の会員 API 契約の有無）
3. **EPRX の対象商品**: 一次・二次①②・三次①②・複合のどれに入札するか
4. **往復効率 η と SOC 上下限**: 仮置き η = 0.85、SOC 5%〜95% で良いか
5. **過去データの入手**: EPRX 約定履歴・時間前約定データは手元にあるか（無ければ公開データの範囲でバックテスト）

### バックテストの約定モデル
JEPX 公開の時間前データは **全エリア合算のコマ別四本値**であり、板や約定明細ではない。
安値 0.01 円のような単発の約定が頻繁に含まれるため、約定判定を 2 通りで計算している:
- **保守的（既定）**: コマの加重平均価格が指値を越えたら約定
- **楽観的**: 高値/安値が指値に触れたら約定
実際の約定は両者の間にあると考えられる。精度を上げるには時間前の約定明細（会員データ）が必要。

### ウォークフォワード検証（v0.4、東京、保守的判定 = 加重平均価格で約定）
| 検証期間（学習 = 直前 60 日） | 学習で選んだオフセット | スポット連動 | v0.2 固定 | 約定数（連動 / 固定） | 参考: スポット裁定の上限 |
|---|---|---|---|---|---|
| 2026/08/16〜09/14 | 買 ±0 / 売 −1 | 63.2 万円 | 10.0 万円 | 140 / 4 | 186.8 万円 |
| 2026/09/15〜10/14 | 買 ±0 / 売 −1（spread 2） | 26.5 万円 | 24.7 万円 | 89 / 16 | 232.2 万円 |
| 2026/10/15〜11/13 | 買 +2 / 売 −3 | 88.4 万円 | 18.9 万円 | 165 / 10 | 259.7 万円 |

- 楽観的判定（高値/安値タッチ）では固定しきい値の方が大きく出る（例 10/15〜: 332 万円）が、これは 0.01 円などの単発約定を
  全量約定とみなすためで、実約定の根拠が弱い。連動方式は保守/楽観の差が小さい（88 万 / 94 万）＝約定見込みが安定している。
- 「スポット裁定の上限」はスポット約定価格を事前に知っていた場合の値で、到達可能な成績ではない。
- 既定値は 3 回中 2 回選ばれた「買 ±0 / 売 −1 円」。10/15〜11/13 を既定値で回すと 60.1 万円（固定 18.9 万円）。

### 売り切り優先の検証（v0.5、東京、保守的判定、在庫補正後の損益）
| 検証期間（学習 = 直前 60 日） | 学習で選ばれた catchupYen | 売り切り優先なし（既定） | 選定値 |
|---|---|---|---|
| 2026/08/16〜09/14 | 0 | 55.9 万円 | 55.9 万円 |
| 2026/09/15〜10/14 | 4（売 +3 / spread 4 と同時選定） | 29.9 万円 | 33.5 万円 |
| 2026/10/15〜11/13 | 0 | 62.2 万円 | 81.1 万円（売 −3 / 買 +2 による改善） |

- 個別の日では効く（ID:20261116: −49,870 円 / 終了 SOC 5.77 → +153,675 円 / 0.40、catchupYen = 2）が、
  多くは翌日に売れていた電気を前倒しで少し安く売るだけなので、期間合計の改善は 3 回中 1 回に留まった。
- このため既定は無効（0）のまま。sweep の選択肢に入れ、月次の選び直しで有効になる形にした。
